## 1. 技术栈与整体架构

### 1.3 请求处理主链路

以 `/v1/chat/completions` 为例（`kiro/routes_openai.py:160`）：

1. `verify_api_key` 校验 `Authorization: Bearer {PROXY_API_KEY}`（`routes_openai.py:68-86`）。
2. 截断恢复注入（`routes_openai.py:185-234`，见第 6 节）。
3. 可选注入 `web_search` 工具（`routes_openai.py:241-272`）。
4. 若开启账号系统进入 **failover 循环**（`routes_openai.py:278-556`）：`account_manager.get_next_account()` 选账号 → `build_kiro_payload()`（`converters_openai.py:393`）构造 Kiro payload → `KiroHttpClient.request_with_retry("POST", url, kiro_payload, stream=True)`（`routes_openai.py:358-363`），URL 为 `{api_host}/generateAssistantResponse`（`routes_openai.py:347`）。
5. 上游 200：流式走 `stream_with_first_token_retry` → `stream_kiro_to_openai_internal`（`streaming_openai.py:72`）；非流式用 `collect_stream_response` 聚合（`streaming_openai.py:576`）。
6. 非 200：`enhance_kiro_error` 提取 reason（`kiro/kiro_errors.py:63`），`classify_error` 分 FATAL/RECOVERABLE（`kiro/account_errors.py:49`），FATAL 直接回客户端，RECOVERABLE 换账号重试。

Anthropic 链路结构完全对称（`routes_anthropic.py:119` 起），区别仅在鉴权头（`x-api-key` 优先，兼容 Bearer，`routes_anthropic.py:73-112`）与转换/流式格式器。

**值得注意的设计**：无论客户端是否要求 stream，对上游**永远以流式方式请求**（`request_with_retry(..., stream=True)`，`routes_openai.py:358-363`）；非流式响应是在网关侧把 SSE 收集聚合出来的。这大大简化了上游交互——上游只有流式一种形态。

### 2.2 认证方式：Bearer token，不是 SigV4

`get_kiro_headers`（`kiro/utils.py:61-89`）构造全部上游请求头：

```
Authorization: Bearer {access_token}
Content-Type: application/x-amz-json-1.0
x-amz-target: AmazonCodeWhispererStreamingService.GenerateAssistantResponse
User-Agent: aws-sdk-js/1.0.27 ua/2.1 os/win32#10.0.19044 lang/js md/nodejs#22.21.1 api/codewhispererstreaming#1.0.27 m/E KiroIDE-0.7.45-{fingerprint}
x-amz-user-agent: aws-sdk-js/1.0.27 KiroIDE-0.7.45-{fingerprint}
x-amzn-codewhisperer-optout: true
x-amzn-kiro-agent-mode: vibe
amz-sdk-invocation-id: {uuid4}
amz-sdk-request: attempt=1; max=3
```

要点：
- **没有 AWS SigV4 签名**。认证就是 OAuth access token 走 Bearer，网关把自己伪装成 Kiro IDE（伪造 aws-sdk-js 的 User-Agent + 机器指纹 `get_machine_fingerprint()`，`utils.py:38-58`）。
- `x-amz-target` 表明这是 AWS JSON 1.0 RPC 协议风格（AmazonCodeWhispererStreamingService.GenerateAssistantResponse）。
- 凭据来源三种（`auth.py`）：JSON 文件（refreshToken/accessToken/profileArn/region，`auth.py:384-456`）、裸 refresh_token、kiro-cli 的 SQLite 库（`auth_kv` 表，键优先级 `kirocli:social:token` > `kirocli:odic:token` > `codewhisperer:odic:token`，`auth.py:54-65,248-382`；profile ARN 还能从 `state` 表 `api.codewhisperer.profile` 的 ARN 里解析出 API region，`auth.py:344-372`）。刷新后回写（read-merge-write，`auth.py:524-632`）。
- token 生命周期：`TOKEN_REFRESH_THRESHOLD=600s` 提前刷新（`config.py:193`），`asyncio.Lock` 防并发刷新（`auth.py:870-934`），403 时 `force_refresh`（`auth.py:936-947`）。

### 2.3 请求体结构（CodeWhisperer 的 conversationState）

最终 payload 在 `converters_core.py:1568-1585` 组装：

```json
{
  "conversationState": {
    "chatTriggerType": "MANUAL",
    "conversationId": "<uuid 或16位hex>",
    "currentMessage": {
      "userInputMessage": {
        "content": "...",
        "modelId": "claude-sonnet-4.5",
        "origin": "AI_EDITOR",
        "images": [{"format": "jpeg", "source": {"bytes": "<base64>"}}],
        "userInputMessageContext": {
          "tools": [{"toolSpecification": {"name": "...", "description": "...", "inputSchema": {"json": {...}}}}],
          "toolResults": [{"content": [{"text": "..."}], "status": "success", "toolUseId": "..."}]
        }
      }
    },
    "history": [
      {"userInputMessage": {"content": "...", "modelId": "...", "origin": "AI_EDITOR", ...}},
      {"assistantResponseMessage": {"content": "...", "toolUses": [{"name": "...", "input": {...}, "toolUseId": "..."}]}},
      ...
    ]
  },
  "profileArn": "arn:aws:codewhisperer:..."
}
```

结构要点：
- **最后一条消息**放在 `currentMessage.userInputMessage`；**之前的所有消息**进 `history`（`converters_core.py:1486-1495`）。
- `history` 元素是 `{"userInputMessage": ...}` / `{"assistantResponseMessage": ...}` 两种单键对象（`build_kiro_history`，`converters_core.py:1320-1398`）。
- 工具定义放在**当前消息**的 `userInputMessageContext.tools`（不是顶层），格式 `{"toolSpecification": {name, description, inputSchema: {json: <schema>}}}`（`converters_core.py:626-632,1533-1535`）。
- tool 结果放 `userInputMessageContext.toolResults`，固定 `status: "success"`，空内容替换为 `"(empty result)"`（`converters_core.py:711-742`）。
- 历史里 assistant 的 tool 调用是 `assistantResponseMessage.toolUses: [{name, input(dict), toolUseId}]`（`converters_core.py:1392-1394`、提取逻辑 `extract_tool_uses_from_message` 772-819）。
- 图片直接挂 `userInputMessage.images`（`{"format": "png", "source": {"bytes": base64}}`），**不放 context**——与 Kiro IDE 原生格式一致（`converters_core.py:641-704,1356-1360,1560-1562`）。
- 若当前消息是 assistant（客户端续写场景），把它塞进 history 再用 `"(empty placeholder)"` 当 current user message（`converters_core.py:1507-1513`）。
- `chatTriggerType` 恒为 `"MANUAL"`，`origin` 恒为 `"AI_EDITOR"`。payload 体积超 `KIRO_MAX_PAYLOAD_BYTES`（默认 600KB，`config.py:487`）时可自动裁剪 history（`payload_guards.py:121-163`：成对弹最老消息、对齐 user 开头、修复孤儿 toolResults）。

### 2.4 响应：AWS event stream 二进制帧 —— 以及本项目"朴素"的解析法

上游响应是 **AWS event-stream（vnd.amazon.eventstream）二进制帧流**：每条消息含 prelude（总长+头长+CRC）、headers（`:message-type: event`、`:event-type: ...`、`:content-type: application/json`）、payload（一段 JSON）、message CRC。JSON payload 的典型形态按事件类型：

- `{"content": "..."}` — 文本增量（assistantResponseMessage 事件的简化载荷）
- `{"name": "...", "toolUseId": "...", "input": ...}` — tool use 开始
- `{"input": "..."}` — tool 输入 JSON 的分片续传
- `{"stop": true}` — tool use 结束
- `{"followupPrompt": "..."}` — 建议追问（被跳过）
- `{"usage": <credits>}` — 计费/credit 消耗
- `{"contextUsagePercentage": <0-100>}` — 上下文占用百分比

**关键发现：本项目并没有真正实现 AWS event-stream 帧解析器**（没有 prelude/CRC/header 解析），而是利用"JSON payload 是 UTF-8 文本、嵌在二进制帧里"这一事实做**文本扫描**（`kiro/parsers.py:211-569`）：

1. `feed(chunk)` 把字节 `chunk.decode('utf-8', errors='ignore')` 追加进字符串 buffer（`parsers.py:268-269`）——帧的二进制头/CRC 字节被 ignore 掉。
2. 用前缀模式表 `EVENT_PATTERNS`（`parsers.py:241-249`：`{"content":`→content、`{"name":`→tool_start、`{"input":`→tool_input、`{"stop":`→tool_stop、`{"followupPrompt":`→followup、`{"usage":`→usage、`{"contextUsagePercentage":`→context_usage）在 buffer 里找**最早出现**的 JSON 起点（`parsers.py:275-287`）。
3. 用 `find_matching_brace`（`parsers.py:39-89`：括号计数 + 字符串/转义感知）找到完整 JSON 对象边界；不完整则等更多数据（`parsers.py:290-296`）。
4. `json.loads` 后按类型分发 `_process_event`（`parsers.py:308-332`）。

事件归一化逻辑（`parsers.py`）：
- content：去重连续重复内容（`last_content` 比较，`parsers.py:343-348`），跳过 followupPrompt。
- tool_start：若上一个 tool call 未完结先 finalize；`input` 可以是 dict（序列化）或字符串（分片起点），以 `toolUseId`（缺省生成 `call_xxxxxxxx`）为 id 开一个新的 `current_tool_call`（`parsers.py:350-380`）。
- tool_input：把分片字符串追加到 `current_tool_call.function.arguments`（`parsers.py:382-395`）。
- tool_stop（`{"stop": true}`）：finalize（`parsers.py:397-401`）。finalize 时尝试把 arguments 解析再序列化以规范化 JSON；失败则诊断是否被上游截断（`_diagnose_json_truncation`，`parsers.py:464-548`：数大括号/中括号平衡、引号奇偶），标记 `_truncation_detected` 并把 arguments 置 `"{}"`（`parsers.py:403-462`）。
- `get_tool_calls()` 收尾时强制 finalize 并 `deduplicate_tool_calls`（按 id 保留参数更全者 + 按 name+args 去重，`parsers.py:151-208,550-562`）。

> 对你 Go 实现的提示：这种"扫 JSON"写法能工作但脆弱（理论上一个 content 字符串里若以 `{"name":` 开头就会被误判）。若要更稳，应按 AWS event-stream 规范解析帧（4 字节总长 + 4 字节头长 + 4 字节 prelude CRC + headers + payload + 4 字节 message CRC），payload 再解 JSON。kiro-gateway 的做法可以作为快速验证，正式实现建议写真正的帧解析器。

## 3. 请求转换层（OpenAI/Anthropic → CodeWhisperer）

### 3.1 两级架构：Adapter → Core

- OpenAI 适配器：`converters_openai.py`；Anthropic 适配器：`converters_anthropic.py`。
- 两者都先转成**统一中间表示**（`converters_core.py` 中的 dataclass）：
  - `UnifiedMessage{role, content, tool_calls, tool_results, images}`（`converters_core.py:83-103`）

### 3.2 OpenAI → Unified（`converters_openai.py`）

- **system**：遍历 messages，所有 `role=="system"` 的文本拼起来（`\n` 连接）成 system_prompt，从消息流中剔除（`convert_openai_messages_to_unified`，`converters_openai.py:156-166`）。
- **tool 消息**（`role=="tool"`）：转换成 `UnifiedMessage(role="user", content="", tool_results=[{type:"tool_result", tool_use_id: msg.tool_call_id, content}])`；连续多个 tool 消息聚合成**一条** user 消息（`pending_tool_results` 缓冲，`converters_openai.py:168-240`）；tool 消息里夹带的图片（MCP 截图）也提取到该 user 消息的 `images`（`converters_openai.py:187-191`）。
- **assistant.tool_calls**：原样保留为 OpenAI 形状的 dict（`converters_openai.py:114-138`）。
- **tools 参数**：兼容标准 `{"type":"function","function":{...}}` 与 Cursor 扁平风格 `{"name","description","input_schema"}`（`converters_openai.py:252-293`）。
- **reasoning_effort** → `ThinkingConfig`：`none` 关闭；其余按 max_tokens 百分比映射预算（minimal 10% / low 20% / medium 50% / high 80% / xhigh 95%）（`converters_openai.py:300-386`）。

### 3.3 Anthropic → Unified（`converters_anthropic.py`）

- **system**：独立字段，支持字符串或 `[{type:"text", text, cache_control}]` 列表（cache_control 被忽略，`converters_anthropic.py:78-113`）。
- **assistant content 里的 `tool_use` block** → 统一 tool_calls（`extract_tool_uses_from_anthropic_content`，`converters_anthropic.py:207-255`）。
- **user content 里的 `tool_result` block** → 统一 tool_results，空内容补 `"(empty result)"`（`converters_anthropic.py:116-162`）；tool_result 内嵌图片也被提取（`converters_anthropic.py:165-202`）。
- **thinking** 参数 → `ThinkingConfig`：`{"type":"enabled","budget_tokens":N}` / `{"type":"disabled"}`（`converters_anthropic.py:373-426`）。
- 入口 `anthropic_to_kiro`（`converters_anthropic.py:429-488`）。

### 3.4 Unified → Kiro payload 的消息规整流水线（`converters_core.py:1435-1495`）

这是整个转换层最有"工程味"的部分，按顺序执行：

1. **长描述工具降级**：description 超过 `TOOL_DESCRIPTION_MAX_LENGTH`（默认 10000 字符，`config.py:321`）的工具，完整描述挪进 system prompt 的 `# Tool Documentation` 段，工具里只留引用（`process_tools_with_long_descriptions`，`converters_core.py:493-557`）。
2. **工具名校验**：超过 64 字符直接 `ValueError` → 400（`validate_tool_names`，`converters_core.py:560-599`）。
3. system prompt 追加"thinking 标签合法化说明"和"截断通知合法化说明"（`converters_core.py:1446-1454`，见第 6 节）。
4. **无 tools 时剥离所有 tool 痕迹**：Kiro 拒绝"有 toolResults 但没 tools"的请求，于是把 tool_calls/tool_results 渲染成 `[Tool: name (id)]\n{args}` / `[Tool Result (id)]\n...` 文本并入 content（`strip_all_tool_content`，`converters_core.py:911-992`；渲染函数 826-904）。
5. **孤儿 tool_results 修复**：tool_results 前面若没有带 tool_calls 的 assistant 消息，同样降级为文本（`ensure_assistant_before_tool_results`，`converters_core.py:995-1068`）。
6. **相邻同 role 消息合并**（Kiro 不接受连续同角色）：content 拼接、tool_calls/tool_results 合并（`merge_adjacent_messages`，`converters_core.py:1071-1152`）。
7. **首条必须是 user**，否则前置 `"(empty placeholder)"` 的 user 消息（`ensure_first_message_is_user`，`converters_core.py:1155-1201`）。
8. **未知 role 归一为 user**（如 `developer`、`system` 漏网者，`normalize_message_roles`，`converters_core.py:1204-1256`）。
9. **强制 user/assistant 交替**：连续 user 之间插入 `(empty placeholder)` 的 assistant（`ensure_alternating_roles`，`converters_core.py:1259-1313`）。
10. **system prompt 注入位置**：拼到 history 第一条 user 消息 content 前面；若无 history 则拼到 current message 前面（`converters_core.py:1488-1493,1501-1503`）。**Kiro 协议没有独立 system 字段，system 只能内联进 user 文本。**
11. 空 content 一律补 `"(empty placeholder)"`（Kiro 要求非空，`converters_core.py:1343-1345,1515-1517`）。
12. **JSON Schema 清洗**：递归删除空 `required: []` 和所有 `additionalProperties`（否则 Kiro 400 "Improperly formed request"）（`sanitize_json_schema`，`converters_core.py:439-486`）；description 为空时补 `Tool: {name}` 占位（`converters_core.py:620-624`）。

## 4. 响应转换

### 4.1 统一事件流（`kiro/streaming_core.py`）

`parse_kiro_stream(response, first_token_timeout)`（`streaming_core.py:118-227`）是两种输出格式共用的解析器：

- 用 `asyncio.wait_for(byte_iterator.__anext__(), first_token_timeout)` 等**首字节**，超时抛 `FirstTokenTimeoutError`（默认 15s，`config.py:354`；`streaming_core.py:153-163`）。
- 每个 chunk 喂给 `AwsEventStreamParser.feed`，输出经 `_process_chunk`（`streaming_core.py:230-282`）变成统一 `KiroEvent`（`streaming_core.py:63-87`：`type ∈ {content, thinking, tool_use, usage, context_usage, error}`）。
- content 事件先过 `ThinkingParser`（`kiro/thinking_parser.py:79+`，状态机 `ParserState`，识别 `<thinking>/<think>/<reasoning>/<thought>` 开标签，`config.py:472`），把"伪 thinking"段从正文里剥出来成为独立 `thinking` 事件；初始 20 字节缓冲防标签被分片切断（`config.py:478`）。
- 流结束后 finalize thinking parser，`parser.get_tool_calls()` 产出的 tool call 逐个 yield 为 `tool_use` 事件（`streaming_core.py:210-216`）——**注意：tool use 不是实时流出的，而是在流末尾一次性产出**（因为解析器要攒齐 input 分片）。
- `usage`（credits）和 `context_usage`（百分比）事件原样透出。
- 通用重试包装 `stream_with_first_token_retry`（`streaming_core.py:369-505`）：首 token 超时则关掉响应、重新发请求，最多 `FIRST_TOKEN_MAX_RETRIES=3` 次（`config.py:366`）；支持复用已验证 200 的 `initial_response`。

### 4.2 → OpenAI SSE（`kiro/streaming_openai.py`）

`stream_kiro_to_openai_internal`（`streaming_openai.py:72-447`）：

- 每个 `content` 事件 → 一个 `chat.completion.chunk`：`choices[0].delta.content`；首个 chunk 额外带 `delta.role="assistant"`（`streaming_openai.py:133-156`）。
- `thinking` 事件：按 `FAKE_REASONING_HANDLING` 配置（`config.py:463-467`）放到 `delta.reasoning_content` 或 `delta.content`（`streaming_openai.py:158-185`）。
- `tool_use` 事件：先攒进 `tool_calls_from_stream`；`web_search` 被拦截走 MCP 仿真（`streaming_openai.py:187-260`，见第 6 节）。
- 流末尾：对累积全文跑 `parse_bracket_tool_calls`（识别 `[Called func with args: {...}]` 文本型工具调用，`parsers.py:92-148`），与流内 tool calls 合并去重（`streaming_openai.py:277-279`）。
- **finish_reason**：内容被截断（流结束但既没收到 usage 也没收到 context_usage 且有正文）→ `length`；有 tool calls → `tool_calls`；否则 `stop`（`streaming_openai.py:271-302`）。
- tool calls 以**单个 chunk** 发出，每个 call 加 `index` 字段（`streaming_openai.py:326-363`）。
- **usage**（最后一个 chunk，`streaming_openai.py:392-416`）：
  - `completion_tokens` = tiktoken 数全文 + thinking（×1.15 修正）。
  - `total_tokens` 优先用上游 `contextUsagePercentage`：`total = pct/100 * maxInputTokens`（上限来自 `ModelInfoCache`，默认 200000，`cache.py:129-142`），`prompt = total - completion`（`calculate_tokens_from_context_usage`，`streaming_core.py:337-362`）。
  - 上游没给 context_usage 时回退 tiktoken 数请求消息+工具（不带修正系数，`streaming_openai.py:317-323`）。
  - 上游 `usage`（credits）放进 `usage.credits_used` 扩展字段（`streaming_openai.py:405-406`）。
- 结尾 `data: [DONE]\n\n`（`streaming_openai.py:417`）。
- 非流式 `collect_stream_response`（`streaming_openai.py:576-688`）：复用流式生成器，解析自己产出的 SSE 文本聚合出标准 `chat.completion`（tool_calls 去掉 index 字段）。

### 4.3 → Anthropic SSE（`kiro/streaming_anthropic.py`）

`stream_kiro_to_anthropic`（`streaming_anthropic.py:129-718`），事件序列严格按 Anthropic Messages streaming 规范：

1. **`message_start`**（`streaming_anthropic.py:206-221`）：空 content，`usage.input_tokens` 用的是**请求侧 tiktoken 估算**（`estimate_request_tokens`），因为上游的准确 context_usage 要到流尾才来（代码注释自承精度 ~85-90%，170-173 行）。
2. **thinking block**（`FAKE_REASONING_HANDLING == "as_reasoning_content"` 时）：`content_block_start{type:"thinking", signature: <伪造 sig_xxx>}` → `content_block_delta{thinking_delta}` → 遇到正文/tool 时 `content_block_stop`（`streaming_anthropic.py:261-289`；signature 是占位符，`generate_thinking_signature`，88-98 行）。
3. **text block**：`content_block_start{type:"text", text:""}` → `content_block_delta{text_delta}`（`streaming_anthropic.py:237-259`）。
4. **tool_use block**：因为上游 tool 是流尾一次性到的，所以是完整的 `content_block_start{type:"tool_use", id, name, input:{}}` → 单个 `content_block_delta{input_json_delta, partial_json: <完整 JSON>}` → `content_block_stop`（`streaming_anthropic.py:486-512`）。id 缺省生成 `toolu_<hex24>`。block index 用 `current_block_index` 单调递增维护。
5. **`message_delta`**：`delta.stop_reason`（截断→`max_tokens`、有 tool→`tool_use`、否则 `end_turn`，637-643 行）+ `usage.output_tokens`（tiktoken 数）；`input_tokens` 若上游给了 context_usage 则在这里被修正（628-635 行）；上游 usage 里的 `cache_read_input_tokens`/`cache_creation_input_tokens`（蛇形或驼峰）透传（`_extract_cache_usage_fields`，101-126 行）。
6. **`message_stop`**（`streaming_anthropic.py:660-663`）。
7. 中途异常 → 发 `event: error`（`streaming_anthropic.py:700-713`）。
8. `web_search` 拦截后发出 `server_tool_use` + `web_search_tool_result` + 文本摘要的完整 block 序列
（续 4.3）

8. **`web_search` 拦截**（`streaming_anthropic.py:355-468`）：发出 `server_tool_use` block（`input_json_delta` 带 query）→ `web_search_tool_result` block（内含 `web_search_result` 数组，snippet 放 `encrypted_content` 字段）→ 文本摘要 block，完整模拟 Anthropic 服务端搜索工具的 SSE 序列。
9. 非流式 `collect_anthropic_response`（`streaming_anthropic.py:721-863`）：用 `collect_stream_to_result`（`streaming_core.py:289-330`）聚合后组装标准 Messages 响应：thinking block 在前（若 `as_reasoning_content` 模式）、text block、tool_use blocks；`stop_reason` 判定逻辑与流式一致（`streaming_anthropic.py:834-840`）。

### 4.4 usage 填写策略对比（小结）

| 字段 | OpenAI | Anthropic | 来源 |
|---|---|---|---|
| prompt/input tokens | 最后 chunk 的 `usage.prompt_tokens` | `message_start`（估算）+ 内部修正 | 优先 `contextUsagePercentage × maxInputTokens / 100 − output`（`streaming_core.py:337-362`），回退 tiktoken |
| completion/output tokens | tiktoken × 1.15 数全文 | 同左 | `kiro/tokenizer.py:45,77-106` |
| credits | `usage.credits_used` 扩展字段 | 不透出（cache 字段除外） | 上游 `{"usage": N}` 事件 |
| cache tokens | 无 | `cache_read_input_tokens` / `cache_creation_input_tokens` 透传 | 上游 usage dict（`streaming_anthropic.py:101-126`） |

## 6. 特殊处理机制

### 6.1 工具调用（tool calling）全链路

- **入口清洗**：schema 递归去 `additionalProperties`、空 `required`（`converters_core.py:439-486`）；工具名 >64 字符 → 400（`converters_core.py:560-599`）；长 description 挪 system prompt（`converters_core.py:493-557`）；空 description 补占位（`converters_core.py:620-624`）。
- **历史映射**：OpenAI assistant.tool_calls / Anthropic tool_use block → `assistantResponseMessage.toolUses[{name, input(dict), toolUseId}]`（`converters_core.py:772-819,1392-1394`）；OpenAI tool 消息 / Anthropic tool_result → 下一条 user 消息的 `userInputMessageContext.toolResults[{content:[{text}], status:"success", toolUseId}]`（`converters_core.py:711-742`）。
- **无 tools 降级**：请求不带 tools 时所有 tool 痕迹渲染为纯文本（`converters_core.py:911-992`），避免 Kiro 400。
- **出口聚合**：流内 `{"name":...}/{"input":...}/{"stop":true}` 三段式拼装（`parsers.py:350-462`）；文本型 `[Called fn with args: {...}]` 兜底解析（`parsers.py:92-148`）；按 id/名称+参数两级去重（`parsers.py:151-208`）。
- **截断感知**：tool arguments JSON 解析失败时诊断是否被上游截断（`parsers.py:464-548`），打 `_truncation_detected` 标记。

### 6.2 流式状态机

- **首 token 超时重试**：`FIRST_TOKEN_TIMEOUT=15s`（`config.py:354`），`asyncio.wait_for` 等首字节（`streaming_core.py:153-163`）；超时则整请求重来，最多 3 次（`stream_with_first_token_retry`，`streaming_core.py:369-505`）。对用户透明（只表现为延迟）。
- **thinking 标签状态机**：`ThinkingParser`（`thinking_parser.py:79-380`），`ParserState` IntEnum（47 行）在 PRE_CONTENT / IN_THINKING 等状态间迁移；`_could_be_tag_prefix`（232 行）+ 初始 20 字节缓冲处理标签跨 chunk 切断；`finalize`（307 行）冲刷残余；输出模式四选一：`as_reasoning_content` / `remove` / `pass` / `strip_tags`（`config.py:463-467`，`thinking_parser.py:351-380`）。
- **伪 thinking 的注入侧**：因为上游协议没有 thinking 概念，网关通过在最后一条 user 消息前注入 `<thinking_mode>enabled</thinking_mode><max_thinking_length>N</max_thinking_length><thinking_instruction>…` 标签（`converters_core.py:361-432`），并在 system prompt 里声明这些标签"不是注入攻击"（`converters_core.py:304-331`），诱导模型输出 `<thinking>…</thinking>` 包裹的推理，再由出口侧剥出。
- **Anthropic block 状态机**：`streaming_anthropic.py:186-192` 维护 `current_block_index` + `thinking_block_started/index` + `text_block_started/index`，遇到异类内容先 stop 旧 block 再 start 新 block（229-248、326-343 行），流尾统一关未闭 block（594-607 行）。

### 6.3 错误处理与重试

- **HTTP 层**（`kiro/http_client.py:170-342`）：403 → `force_refresh()` 刷新 token 重试；429 / 5xx → `BASE_RETRY_DELAY × 2^attempt` 指数退避（1s/2s/4s）；超时与连接错误经 `network_errors.classify_network_error` 判定可重试性；重试耗尽后 429/5xx 把**最后一个响应原样返回**给上层分类（304-311 行），网络错误抛 502/504 `HTTPException`（327-342 行）。流式请求加 `Connection: close` 头防 CLOSE_WAIT 泄漏（229 行，issue #38）。
- **Kiro 错误语义**（`kiro/kiro_errors.py:63-138`）：解析 `{"message","reason"}`，已知 reason 映射友好文案：`CONTENT_LENGTH_EXCEEDS_THRESHOLD`（上下文超长）、`MONTHLY_REQUEST_COUNT`（月度配额）、`INVALID_MODEL_ID`（模型不可用/订阅不足）、"Improperly formed request."（payload 畸形，提示可能与工具/schema 有关）。
- **failover 分类**（`kiro/account_errors.py:49-134`）：RECOVERABLE（402/403/429/400+INVALID_MODEL_ID → 换账号）vs FATAL（400 其他/422/5xx → 直接回客户端）。

### 6.4 模型名映射

见 3.5 节。补充：`/v1/models` 聚合所有账号的可用模型（`account_manager.py:883-897`、`routes_openai.py:139-157`）；`HIDDEN_FROM_LIST=["auto"]` 隐藏原生名只露别名（`config.py:263`）；`report_success` 时把成功模型动态学习进 `model_to_accounts` 映射（`account_manager.py:788-797`）。

### 6.5 多账号轮换（`kiro/account_manager.py`）

- **凭据来源**：`credentials.json` 数组，三种 type：`json`（路径）、`sqlite`（kiro-cli 库）、`refresh_token`（裸 token）；支持目录扫描（`load_credentials`，215-326 行）；refresh_token 账号 id 用 sha256 前 16 位保证确定性（262-268 行）。
- **启动**：lifespan 里从 `_current_account_index` 起整圈尝试初始化，直到一个成功（`main.py:471-500`）；其余账号**懒初始化**（`get_next_account` 里 `_initialize_account`，`account_manager.py:737-743`）。
- **选择策略**（`get_next_account`，645-763 行）：
  - 单账号：直通，不做熔断（665-698 行）。
  - 多账号：**全局 sticky**——一个 `_current_account_index` 对所有模型生效，从该索引起环形遍历；排除本轮已试过的账号（`exclude_accounts`）。
  - **熔断**：`failures>0` 的账号冷却 `ACCOUNT_RECOVERY_TIMEOUT × 2^(failures-1)`（60s 起、上限 1 天，`config.py:528-532`）；冷却期内仍有 10% 概率试探（probabilistic retry，`config.py:537`）；冷却过期进 Half-Open。
  - **模型缓存 TTL**：仅在使用账号时惰性刷新（`ACCOUNT_CACHE_TTL=12h`，`config.py:545`；runtime 端点直接用静态表，593-600 行）。
- **回报**：`report_success` 清零 failures + 更新 sticky 索引（765-807 行）；`report_failure` 只对 RECOVERABLE 累加 failures，`INVALID_MODEL_ID` 不算账号故障（832-842 行）。
- **failover 循环**：路由侧 `MAX_ATTEMPTS = 账号数 × 2`，RECOVERABLE 换账号重试，FATAL 立即返回；网络错误（502/504）也按 RECOVERABLE 处理（`routes_openai.py:292-556`、`routes_anthropic.py:316-560` 同构）。
- **状态持久化**：`state.json` 每 10s 脏检查后台保存（`save_state_periodically`，418-430 行），tmp+rename 原子写。

### 6.6 其他值得一提的机制

- **截断恢复**（`truncation_state.py` / `truncation_recovery.py`）：检测上游截断后，把信息按 `tool_call_id` 或内容 hash 暂存；客户端下一请求带同名 tool_result / 相同 assistant 内容时，网关在请求里注入 `[System Notice]`/`[API Limitation]` 提示告知模型（`routes_openai.py:185-234`、`routes_anthropic.py:156-249`），并在 system prompt 里预先声明这类提示合法（`converters_core.py:334-358`）。`conversation_id` 可从消息历史生成稳定 16 位 hash（`utils.py:102-163`）。
- **web_search 双路径**（`mcp_tools.py`）：Path A 拦截 Anthropic 原生 `web_search_*` server-side 工具，直接调 Kiro `POST {q_host}/mcp`（JSON-RPC `tools/call`，`mcp_tools.py:77-202`）后合成完整响应/SSE；Path B 自动注入普通 `web_search` function 工具，在流里拦截模型对它的调用、执行 MCP 搜索、以文本摘要/sse block 形式回灌（`streaming_openai.py:187-260`、`streaming_anthropic.py:355-468`）。注意 `result.content[0].text` 是 JSON **字符串**需二次解析（`mcp_tools.py:184-186`）。
- **调试体系**：`debug_middleware.py` 在 Pydantic 校验前捕获请求体（连 422 也能记录），`debug_logger.py` 记录原始 chunk / 修改后 chunk / Kiro payload，错误时 `flush_on_error`。
- **VPN/代理**：`VPN_PROXY_URL` 在创建任何 httpx client 之前写入 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 环境变量，并把 localhost 加进 `NO_PROXY`（`main.py:187-205`）。

## 7. 对你 Go 版 relay gateway 的要点提炼

1. **上游只有流式一种形态**：非流式 = 网关侧聚合。端点 `POST https://runtime.{region}.kiro.dev/generateAssistantResponse`，`x-amz-target: AmazonCodeWhispererStreamingService.GenerateAssistantResponse`，`Content-Type: application/x-amz-json-1.0`，**Bearer token 即可，无需 SigV4**，但要伪装 Kiro IDE 的 aws-sdk-js User-Agent。
2. **请求体核心**是 `conversationState{chatTriggerType:"MANUAL", conversationId, currentMessage.userInputMessage{content, modelId, origin:"AI_EDITOR", images, userInputMessageContext{tools, toolResults}}, history[]}` + 顶层 `profileArn`；system prompt 内联进首条 user 消息；tools 挂在当前消息的 context 里。
3. **event-stream 解析**：本项目用"UTF-8 忽略错误 + JSON 前缀扫描 + 括号配平"的朴素法（`parsers.py`），能用但不严谨；Go 实现建议按 AWS event-stream 帧格式（prelude 12 字节 + headers + payload + CRC32）正经解析，payload 再解 JSON。事件载荷类型：content / name+toolUseId+input / input / stop / usage / contextUsagePercentage / followupPrompt。
4. **消息规整流水线是兼容性的关键**：相邻同 role 合并、首条必须 user、强制交替、空内容占位、孤儿 toolResults 降级文本、无 tools 时剥离 tool 痕迹、schema 去 `additionalProperties`、工具名 ≤64、payload ≤~600KB。
5. **usage 是估算的**：上游只给 credits 和 contextUsagePercentage，token 数 = 百分比 × maxInputTokens 反推或本地 tokenizer 估算；Anthropic 的 `message_start.input_tokens` 不得不用请求侧估算值。
6. **tool_use 在上游流里是"开始-分片-停止"三段式**，而本项目在流尾一次性输出到 OpenAI/Anthropic；若你要做真正的增量 tool 流（input_json_delta 分片透传），需要比它更进一步。
