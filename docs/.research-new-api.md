## 1. 整体架构

### 1.1 分层总览

协议转换相关代码分四层：

| 层 | 位置 | 职责 |
|---|---|---|
| 入口/调度 | `controller/relay.go`、`router/relay-router.go` | 按 URL 确定客户端协议格式（RelayFormat），做鉴权、计费预扣、重试 |
| 中转主流程 | `relay/*.go`（`compatible_handler.go`、`claude_handler.go`、`gemini_handler.go`、`responses_handler.go` 等） | 每种客户端协议一个 Helper：模型映射 → 调 adaptor 转换请求 → 转发 → 调 adaptor 转换响应 |
| 渠道适配器 | `relay/channel/<provider>/`（40+ 个目录） | 每个上游一个 `Adaptor`：URL、鉴权头、请求转换、响应/流处理 |
| 转换引擎（独立 Go module） | `relaykit/`（`relaykit/dto`、`relaykit/relayconvert`、`relaykit/types`） | 所有协议 DTO + 注册表式 A→B 转换器。注意 `relaykit` 有自己的 `go.mod`，是独立模块 |

关键设计：**2024 年后该项目把核心的文本协议转换抽成了独立模块 `relaykit/relayconvert`，采用"注册表 + 格式路由"模式**，不再是每个 adaptor 各写各的转换函数。

### 1.2 请求调度流程（以一次 /v1/chat/completions 为例）

1. **路由确定 RelayFormat**：`router/relay-router.go:79-192` 按路径调用 `controller.Relay(c, types.RelayFormatXxx)`。`/v1/messages` → `RelayFormatClaude`（第 91 行），`/v1/chat/completions` → `RelayFormatOpenAI`（96），`/v1/responses` → `RelayFormatOpenAIResponses`（~99），`/v1beta/models/:model:generateContent` 等 → `RelayFormatGemini`（146/149/192）。
2. **Relay 入口**：`controller/relay.go:73` `Relay()`。流程：
   - `helper.GetAndValidateRequest(c, relayFormat)`（relay.go:114）按格式把 body 解析成对应 DTO（`*dto.GeneralOpenAIRequest` / `*dto.ClaudeRequest` / `*dto.GeminiChatRequest` 等）；
   - `relaycommon.GenRelayInfo(c, relayFormat, request, ws)`（relay.go:125；实现在 `relay/common/relay_info.go:616`）构造 `RelayInfo`，其中 `RelayFormat` 记录**客户端协议**（relay_info.go:126）；
   - token 估算、定价、预扣费（relay.go:150-173）；
   - **重试循环**（relay.go:196-246）：`getChannel()` 选渠道 → 按格式分发到 `relay.TextHelper` / `relay.ClaudeHelper` / `geminiRelayHandler` / `relay.WssHelper`（relay.go:222-231）；失败时 `shouldRetry()` 判断换渠道重试。
3. **渠道 → 上游协议**：渠道记录里的 channel type 经 `common.ChannelType2APIType`（`common/api_type.go:5`）映射为 `ApiType`，存进 `RelayInfo.ApiType`（`relay/common/relay_info.go:219-226`）。**ApiType 决定目标上游协议**。
4. **Helper 主流程**（三种格式结构完全同构，以 OpenAI 为例 `relay/compatible_handler.go:25` `TextHelper`）：
   - `info.InitChannelMeta(c)`（26）填充渠道元信息；
   - `common.DeepCopy` 复制请求（33），避免重试间污染；
   - `helper.ModelMappedHelper(c, info, request)`（42）做模型名映射，把 `info.UpstreamModelName` 写回 request（`relay/helper/model_mapped.go:14-69`，支持链式映射与环检测）；
   - `adaptor := GetAdaptor(info.ApiType)`（70）→ `relay/relay_adaptor.go:50` 的大 switch，按 ApiType 返回对应 channel adaptor；
   - `adaptor.ConvertOpenAIRequest(c, info, request)`（112）把客户端请求转成上游格式；
   - 转换结果 marshal 成 JSON，再经过 `RemoveDisabledFields`（按渠道配置删字段，128）和 `ApplyParamOverrideWithRelayInfo`（参数覆盖，134）；
   - `adaptor.DoRequest`（153）发 HTTP（默认实现 `channel.DoApiRequest`，`relay/channel/api_request.go:313`：`GetRequestURL` → `SetupRequestHeader` → header override → 发送）；
   - 非 200 → `service.RelayErrorHandler`（`service/error.go:87`）解析上游错误；
   - `adaptor.DoResponse`（171）处理响应（含流），返回 `*dto.Usage`；
   - `service.PostTextConsumeQuota`（184）按 usage 结算。

   Claude 入口 `relay/claude_handler.go:22` `ClaudeHelper` 与 Gemini 入口 `relay/gemini_handler.go:22` `GeminiHelper` 结构相同，只是改调 `adaptor.ConvertClaudeRequest` / `adaptor.ConvertGeminiRequest`，且 Claude 有渠道级 system prompt 注入逻辑（claude_handler.go:51-74）、Gemini 有 `SystemInstructions` 注入（gemini_handler.go:51-89）。

   另有透传模式：全局 `PassThroughRequestEnabled` 或渠道 `PassThroughBodyEnabled` 时跳过转换，直接重放原始 body（compatible_handler.go:100-110；claude_handler.go:89-95）。

### 1.3 Adaptor 接口

`relay/channel/adapter.go:17-34`：

```go
type Adaptor interface {
    Init(info *relaycommon.RelayInfo)
    GetRequestURL(info *relaycommon.RelayInfo) (string, error)
    SetupRequestHeader(c *gin.Context, req *http.Header, info *relaycommon.RelayInfo) error
    ConvertOpenAIRequest(c, info, request *dto.GeneralOpenAIRequest) (any, error)
    ConvertRerankRequest(...) / ConvertEmbeddingRequest(...) / ConvertAudioRequest(...) / ConvertImageRequest(...)
    ConvertOpenAIResponsesRequest(c, info, request dto.OpenAIResponsesRequest) (any, error)
    DoRequest(c, info, requestBody io.Reader) (any, error)
    DoResponse(c, resp *http.Response, info) (usage any, err *types.NewAPIError)
    GetModelList() []string
    GetChannelName() string
    ConvertClaudeRequest(c, info, request *dto.ClaudeRequest) (any, error)
    ConvertGeminiRequest(c, info, request *dto.GeminiChatRequest) (any, error)
}
```

即每个 adaptor 必须实现"四种客户端格式（OpenAI chat、OpenAI responses、Claude、Gemini）的请求转换入口"，不支持的返回 `not implemented`。`DoResponse` 内部根据 `info.RelayFormat`（客户端要什么）和 `info.IsStream` 分支。

另有 `TaskAdaptor`（adapter.go:36-81）用于异步任务类上游（视频生成等，JS 插件驱动），与文本转换无关。

### 1.4 转换引擎（relaykit/relayconvert）的注册表设计

这是本项目最值得借鉴的部分。`RelayFormat` 类型定义在 `relaykit/types/relay_format.go:3-20`：`openai`、`claude`、`gemini`、`openai_responses` 等。

**请求侧**：`relaykit/relayconvert/request_registry.go`
- `RequestConverterSpec{ID, From, To, Quality, Convert, StepConverters}`（48-55）。`Convert` 是直接转换函数；`StepConverters` 是**多跳转换链**（如 Claude→Gemini = Claude→OpenAI + OpenAI→Gemini）。
- `registerBuiltinRequestConverter`（89）注册并做严格校验：route 唯一、step 链首尾衔接（114-135），冲突直接 panic。
- 入口 `ConvertRequest(c, info, target, request)`（155）：用 `convmeta.GuessRelayFormatFromRequest` 按 Go 类型推断源格式（409-418），同格式直接返回，否则查路由执行。多跳执行在 `executeRequestSteps`（242-305）：**转换前先用 `toolconv.ExtractRequest` 把工具定义从源请求中剥离成工具 IR，逐跳转换 messages，最后用 `toolconv.AttachRequest` 按目标格式重新编码工具**——工具系统因此只需写"格式↔IR"两套编解码，而不是 N²。
- 每次转换产生 `RequestResult{Value, From, To, Converter, Quality, Steps, Diagnostics}`（38-46），Diagnostics 记录有损转换告警。

**响应侧**：`relaykit/relayconvert/response_registry.go`
- `ResponseConverterSpec`（58-69）比请求侧多三个流式钩子：`ConvertStream`（无状态整 chunk 转换）、`NewStreamState` + `ConvertStreamChunk`（有状态逐 chunk）、`FinalizeStream`（流结束时冲刷残余事件）。
- `ConvertResponse`（231）非流式；`ConvertStreamResponse`（272）无状态流式；`NewResponseStreamState`（297）+ `ConvertStreamResponseChunk`（326）+ `FinalizeStreamResponse`（360）是有状态流式管线，内部 `ResponseStreamState`（95-109）持有逐步 step 状态、累计 usage、去重后的 diagnostics。多跳流式时一个 chunk 依次流过各 step（`executeResponseStreamSteps`，607-631）。

**内置路由表**：`relaykit/relayconvert/text_converter_registry.go:49-252` `builtinTextConverters`，一次性把请求+响应两侧一起注册（`registerBuiltinTextConverter`，272-319）。共 11 条路由：

| From → To | 质量标注 | 实现方式 |
|---|---|---|
| Claude → OpenAI chat | fair | 直接（51-65） |
| OpenAI chat → Claude | fair | 直接（67-80） |
| Gemini → OpenAI chat | fair | 直接（82-97） |
| OpenAI chat → Gemini | fair | 直接（99-114） |
| OpenAI chat → OpenAI responses | good | 直接（116-130） |
| OpenAI responses → OpenAI chat | good | 直接（132-146） |
| Claude → Gemini | discouraged | 多跳：Claude→OAI→Gemini（148-165） |
| Claude → OpenAI responses | fair | 请求直接转；响应多跳（167-181） |
| Gemini → Claude | discouraged | 多跳（183-200） |
| Gemini → OpenAI responses | fair | 多跳（202-219） |
| OpenAI responses → Claude | fair | 直接（221-235） |
| OpenAI responses → Gemini | fair | 请求直接转；响应多跳（237-251） |

可见 **OpenAI Chat Completions 是事实上的枢纽格式（hub）**：不直连的格式对都经它中转。

**host 侧薄封装**：`service/request_converter.go:26-48`、`service/response_converter.go:10` 把 gin context 和 `*relaycommon.RelayInfo` 适配成 relayconvert 的 `convmeta.Meta` 接口，并记录 diagnostics。`service/request_converter.go:14-24` 的 init 还注入了媒体文件解析器（relaykit 本身不依赖 gin）。

**老 API 兼容层**：`relaykit/relayconvert/response_compat.go` 导出一批 `ResponseOpenAI2Claude`、`StreamResponseClaude2OpenAI` 等自由函数，channel 层大量直接调用它们（不走注册表）。

## 3. 请求转换详解

### 3.1 Anthropic → OpenAI（`ClaudeMessagesRequestToOpenAIChat`）

`relaykit/relayconvert/internal/claude_messages/to_oai_chat_req.go:26-231`，由 `claude` 以外的 adaptor 经 `service.ConvertRequest(c, info, types.RelayFormatOpenAI, claudeReq)` 触发（如 openai adaptor `relay/channel/openai/adaptor.go:57-91`）。逐字段：

- **标量参数**（27-42）：`model`、`temperature` 直拷；`max_tokens`→`MaxTokens`；`top_p`/`top_k` 指针转拷；`stream` 转拷。
- **推理/思考参数**（43-93）：`claudeRequestReasoningIntent` 把 Claude `thinking{type,budget_tokens}` 解析成统一 `reasoning.Intent`；若目标是 OpenRouter 方言（`convmeta.OptionsOf(info).OpenRouterDialect`，48），编码为 OpenRouter 的 `reasoning{enabled,effort,max_tokens,exclude}` JSON（49-75）；否则 `reasoning.ApplyToOpenAIChat` 写成 `reasoning_effort` 等 OpenAI 风格字段（77）。还会保留 `-thinking` 模型名后缀以便下游级联 new-api 还原（84-89）。
- **stop**（95-99）：`stop_sequences` 长度为 1 时写成字符串，>1 时写成数组（OpenAI `stop` 两种形态都接受）。
- **tools**（101-114）：每个 Claude tool（`{name, description, input_schema}`）映射为 `{type:"function", function:{name, description, parameters: input_schema}}`。注意这里只做普通 function；web_search 等服务端工具由 toolconv 的 Attach 阶段处理。
- **system**（117-154）：字符串 system → 一条 `role:system` 文本消息；数组 system 默认把所有 text block **拼接成一个字符串**；OpenRouter 且模型名 `anthropic/claude` 前缀时保留为 media 数组以携带 `cache_control`（130-141）。
- **messages**（156-227）：逐条映射 content block：
  - `text`/`input_text` → `{type:"text", text}`（172-178），保留 cache_control；
  - `image`（base64 source）→ `{type:"image_url", image_url:{url:"data:<mime>;base64,<data>"}}`（179-185）；
  - `tool_use` → 该消息上的 OpenAI `tool_calls` 条目，`input` 对象 marshal 成 JSON 字符串作 `arguments`（186-195）；
  - `tool_result` → 独立的 `role:"tool"` 消息，`tool_call_id` 回填，名称缺失时用 `SearchToolNameByToolCallId` 从请求上下文中反查（196-213）；
  - 同时有 media 和 toolCalls 时只挂 toolCalls（220-222）；空消息被丢弃（224-226）。

逆向（OpenAI → Anthropic）见 `relaykit/relayconvert/internal/oai_chat/to_claude_messages_req.go:17` `OpenAIChatRequestToClaudeMessages`：
- tools：`function.parameters` → `input_schema`（21-30）；OpenAI `web_search_options` 会**合成一个 Anthropic 服务端工具 `web_search_20250305`**，含 user_location 映射（32-65）；
- max_tokens 优先取 `max_completion_tokens`，其次 `max_tokens`（75-79）；`tool_choice` + `parallel_tool_calls` 经 `sharedclaude.MapOpenAIToolChoice` 映射（90-95）；
- reasoning 经 `reasoning.FromOpenAIChat` + `sharedclaude.ApplyReasoning` 转成 Claude `thinking`（97-103）；MaxTokens 缺失时先尝试渠道默认值，最后兜底返回 `ErrMissingMaxTokens`（104-109、320-322）——Claude 必填 max_tokens；
- stop 字符串/数组 → `stop_sequences`（111-122）；
- role 规整（128-147）：`developer`→`system`，`function`→按有无 tool_call_id 分派 `tool`/`user`，未知 role → `user`；
- 相邻同 role 消息合并（158-163）、空 content 填 `"..."`（164-166）——规避 Anthropic 对交替 role/非空内容的校验；
- 所有 system 消息聚合成顶层 `system` 数组（184-204、312-314）；
- **首条必须是 user**：不是则在前面插入占位 user 消息（206-211、174-182）；
- `tool` 消息并入前一条 user 消息的 `tool_result` content block（216-234）；
- 图片/文件经 `relaymedia.ResolveBase64Data` 下载并转 base64，PDF → `document` block，其余 → `image` block（261-285）；
- assistant 的 `tool_calls` → `tool_use` block，`arguments` JSON 反序列化成 `input` 对象（288-303）。

### 3.2 Gemini → OpenAI（`GeminiGenerateContentRequestToOpenAIChat`）

`relaykit/relayconvert/internal/gemini_chat/to_oai_chat_req.go:14-195`：

- **role 映射**（279-290）：`user→user`、`model→assistant`、`function→function`、其他→user。
- **parts 映射**（69-118）：`text` → text content（`thought:true` 的 part 单独聚合成 `reasoning_content`，70-74、127-130）；`inlineData`/`fileData` → `image_url`（data URI 或 URI 直传，80-99）；`functionCall` → `tool_calls` 条目；`functionResponse` → `role:"tool"` 消息。
- **function call ID 合成**：Gemini 历史上没有 tool call ID，`geminiFunctionCallHistory`（206-277）在转换前扫描全部 contents 预留已有 ID，然后为每个 call 生成 `call_N` 并按"名称匹配 + 同名称按顺序"把 functionResponse 关联回去（241-255）。
- **generationConfig → OpenAI 参数**（139-156）：temperature/topP/topK/maxOutputTokens→max_tokens/candidateCount→n 直拷；`stopSequences` **截断到 4 条**（152，OpenAI 限制）。
- **tools**（158-184）：`functionDeclarations` 数组展平成 OpenAI tools。
- **systemInstruction**（186-192）：parts 文本 join 成一条 system 消息插到最前。
- **thinking**：`thinkingConfig` 经 `reasoning.FromGemini`/`ApplyToOpenAIChat` 转成 OpenAI reasoning 字段（25-57）。

### 3.4 转换后的后置处理

转换结果统一经过（以 compatible_handler.go 为例）：
1. `relaycommon.AppendRequestConversionFromRequest`（116）记录转换链到 `info.RequestConversionChain`；
2. `relaycommon.RemoveDisabledFields`（128）按渠道配置删 JSON 字段（如 service_tier、safety_identifier 等默认过滤字段，见 DTO 注释 openai_request.go:60-70）；
3. `relaycommon.ApplyParamOverrideWithRelayInfo`（134）应用渠道级参数覆盖。

渠道特有预处理在各 adaptor 里，如 claude adaptor 的 `ConvertClaudeRequest`（`relay/channel/claude/adaptor.go:35-53`）：max_tokens=0 置 nil、`ApplyClaudeThinkingModel` 处理 thinking 模型、按模型配置默认 max_tokens（`model_setting.GetClaudeSettings().GetDefaultMaxTokens`）。AWS adaptor（`relay/channel/aws/adaptor.go:41-80`）额外把 Claude 消息里的 url 图片全部下载转 base64（Bedrock 不支持 URL source）。

## 4. 响应转换详解

### 4.1 非流式

- **Claude → OpenAI**：`claude_messages/to_oai_chat_resp.go:218` `ResponseClaude2OpenAI`：遍历 `content[]`，`tool_use`→`tool_calls`（input marshal 成 arguments 字符串）、`thinking`→`reasoning_content`、text 拼接成单字符串并转换 citations 为 OpenAI annotations（含 UTF-8 rune offset 计算，254-263）；`stop_reason` 经 `reasonmap.ClaudeStopReasonToOpenAIFinishReason` 映射（映射表在 `relaykit/reasonmap/`：end_turn→stop、max_tokens→length、tool_use→tool_calls、refusal→content_filter 等）。
- **OpenAI → Claude**：`oai_chat/to_claude_messages_resp.go:449` `ResponseOpenAI2Claude`：reasoning_content→thinking block、text→text block（annotations→citations）、tool_calls→tool_use（arguments 反序列化成 input map，失败则空 map）、usage 经 `sharedclaude.UsageFromOpenAI` 转换。
- **Gemini → OpenAI**：`gemini_chat/to_oai_chat_resp.go:81` `ResponseGeminiChat2OpenAI`：inlineData 图片写成 markdown `![image](data:...)`（118-133）、executableCode/codeExecutionResult 写成代码块（142-153）、thought part→reasoning_content；finishReason 映射 STOP→stop、MAX_TOKENS→length、SAFETY 系列→content_filter（166-177）；groundingMetadata→annotations（181）。
- host 入口示例：claude channel 非流式 `relay/channel/claude/relay-claude.go:310-393` `HandleClaudeResponseData`，按 `info.RelayFormat` 分派：OpenAI 用 `ResponseClaude2OpenAI`，Responses/Gemini 走 `service.ConvertResponse`，Claude 直接透传原始 body（363）。

### 4.2 流式（SSE）

**通用读流框架**：`relay/helper/stream_scanner.go:77` `StreamScannerHandler`——三 goroutine 结构（scanner 读行、data handler 处理、可选 ping 保活），按行扫描取 `data:` 前缀（254-265），收到 `[DONE]` 或 EOF/超时/客户端断开时停止，并往 `info.StreamStatus` 记录结束原因（`relay/common/stream_status.go`）。写流辅助函数在 `relay/helper/common.go`：`ObjectData`（125）、`StringData`（97）、`ClaudeData`（61，按 Anthropic SSE 的 `event:` + `data:` 双行格式）、`Done`（136）。

**Claude 流 → OpenAI 流**（claude 渠道 + OpenAI 客户端）：
- 每个 SSE data 解析成 `dto.ClaudeResponse`（一个 Type 字段区分 message_start/content_block_start/content_block_delta/message_delta/message_stop 的统一结构，dto/claude.go:510-525）。
- 逐事件转换：`claude_messages/to_oai_chat_resp.go:34` `StreamResponseClaude2OpenAI`：message_start→带 role 的空 delta；content_block_start(tool_use)→带 ID/name 的 tool_call 首帧；content_block_delta 按 delta.type 分派——`text_delta`→content、`input_json_delta`→tool_call arguments 增量、`thinking_delta`/`signature_delta`→reasoning_content、`citations_delta`→annotations；message_delta→finish_reason；message_stop→nil（不下发）。
- **索引重映射状态机**：`ClaudeToChatStreamState`（同文件 126-207）。Anthropic 的 content block index 是全局递增的（text/thinking/tool 混编），OpenAI tool_calls 的 index 是工具内独立的稠密索引，所以状态里维护 `toolIndexByContentBlock` 映射；`server_tool_use`/`mcp_tool_use`/`*_tool_result` 等 hosted 工具块被静默丢弃（209-216）；delta 引用未知 block 索引时报错（196-198）。
- host 侧：`relay/channel/claude/relay-claude.go:87-161` `HandleStreamResponseData` 按 RelayFormat 分派；`FormatClaudeResponseInfo`（to_oai_chat_resp.go:495-564）同时负责从 message_start/message_delta 累计 usage、拼接全文、回填响应 id/model/created。流结束 `HandleStreamFinalResponse`（relay-claude.go:234-285）：usage 不完整时用 `service.ResponseText2Usage` 本地估算补全，OpenAI 客户端需要时补发一个纯 usage 的最终 chunk（`helper.GenerateFinalUsageResponse`），再发 `[DONE]`。

**OpenAI 流 → Claude 流**（openai 渠道 + Claude 客户端）：
- 这是反向的状态机，更复杂：`oai_chat/to_claude_messages_resp.go:111` `StreamResponseOpenAI2Claude`，状态存在 `convmeta.ClaudeConvertInfo`（`EnsureClaudeConvertInfo()`，跨 chunk 挂在 RelayInfo 上）。
- 第一帧合成 `message_start`（185-213），usage 优先用上游真实值，否则用预估算的 prompt tokens。
- 核心不变式：**Anthropic 要求每个 block 遵循 start→delta*→stop**，所以每次内容类型切换（text↔thinking↔tools）时先 `stopOpenBlocksAndAdvance`（137-154）补发 `content_block_stop` 并推进 index。
- tool_calls：OpenAI 并行工具按 index 分流，`ToolCallByIndex`/`ToolCallByID` 双索引跟踪（264-293）；**id 和 name 齐了才发 `content_block_start`，之前攒的 arguments 存 `PendingArguments` 随后以 `input_json_delta` 补发**（294-324）——解决 OpenAI 首帧只带 id/name、arguments 后续才到的时序问题；id 缺失时合成 `toolu_<uuid>`（57-59）。
- reasoning_content → thinking block + `thinking_delta`；text → text block + `text_delta`（341-385）。
- 结束：finish_reason 到了但 usage 没到时**不发终止帧**，等 usage-only chunk 到了才一起发 `message_delta`（带 usage + stop_reason）+ `message_stop`（393-414）；`FinalizeStreamResponseOpenAI2Claude`（420-447）兜底：流异常结束时强制 stop 所有打开的 block 并补 message_delta/message_stop，stop_reason 缺省 `end_turn`。
- host 侧：`relay/channel/openai/helper.go:39-60` `handleClaudeFormat` 逐 chunk 调 `service.ConvertStreamResponse`，用 `helper.ClaudeData` 逐事件写出；`HandleFinalResponse`（192-262）处理最后一帧。

**Gemini 流 → OpenAI 流**：`gemini_chat/to_oai_chat_resp.go:188` `StreamResponseGeminiChat2OpenAI` 逐 chunk 转换；host 在 `relay/channel/gemini/relay-gemini.go:254` `GeminiChatStreamHandler`，其中自己做了一层"choice→tool id→稠密 index"重映射（275-296），并在首帧前注入 `GenerateStartEmptyResponse`（299-331）；若客户端是 Claude，则先转成 OpenAI chunk 再走上面那条 OpenAI→Claude 管线（`handleStream` → `openai.HandleStreamFormat`，146-156）——即 **Gemini→Claude 流是 Gemini→OpenAI→Claude 两段串联**。

**Claude 流 → OpenAI Responses 流**：`relay/channel/claude/relay_responses.go:19` `ClaudeResponsesStreamHandler` 用 `relayconvert.NewResponseStreamState(RelayFormatClaude, RelayFormatOpenAIResponses, ...)` 建状态管线，hosted 工具（服务端 web_search 等）由 `ClaudeHostedStreamBridge` 桥接（response_compat.go:22-26、58-98）。OpenAI Responses 事件的逐 chunk 状态机在 `oai_chat/to_oai_responses_stream_resp.go`（862 行）和 `oai_responses/to_oai_chat_stream_resp.go`（934 行）。

### 4.3 usage / token 统计

- 统一 usage DTO：`dto.Usage`（`relaykit/dto/openai_response.go:228`），扩展字段含 `PromptTokensDetails.CachedTokens/CachedCreationTokens`、`ClaudeCacheCreation5mTokens/1hTokens`、`UsageSemantic`（"anthropic"/"openai"）、`BillingUsage`。
- Claude→OpenAI：`UsageFromClaudeAPIUsage`（to_oai_chat_resp.go:291-353）：input→prompt、output→completion、cache_read→CachedTokens、cache_creation（含 5m/1h 拆分归一化 `NormalizeCacheCreationSplit`）→CacheWriteTokens，且把 prompt 重算为 input+cache_read+cache_write 的总输入口径。
- Gemini→OpenAI：`UsageFromGeminiMetadata`（gemini_chat/to_oai_chat_resp.go:14-79）：ThoughtsTokenCount 计入 completion 并写入 `CompletionTokenDetails.ReasoningTokens`，按 modality 拆分 text/audio/image tokens。
- 流式 usage 缺失兜底：Claude 流 `HandleStreamFinalResponse`（relay-claude.go:234-256）、Gemini 流（relay-gemini.go:220-234，图片按 1400 token/张估算）都在上游没给 usage 时用本地 tokenizer 估算。Bedrock 等上游 `message_delta` 缺 input_tokens 时，`PatchClaudeMessageDeltaUsageData`（to_oai_chat_resp.go:461-493，用 gjson/sjson 打补丁）把累计值补回透传给客户端的事件里。
- usage 累计用 `dto.MergeUsageNonZero`（`relaykit/dto/usage_merge.go`）——后到的非零字段覆盖、零/缺失不擦除。

### 5.2 有没有统一 IR？

**没有全量消息级 IR，是 A→B 两两（+枢纽中转）转换**。具体策略分三层：

1. **消息体**：直接 DTO→DTO 转换函数（如 `ClaudeMessagesRequestToOpenAIChat`），不经过中间表示。对未直连的格式对，用 `StepConverters` 声明多跳链，以 **OpenAI Chat Completions 为枢纽**（text_converter_registry.go:148-219，Claude↔Gemini 都经 openai 中转）。
2. **工具系统有 IR**：`relaykit/relayconvert/internal/toolconv/model.go` 定义了格式无关的工具中间表示——`Definition{Kind, Execution(client/server), Function, WebSearch, ...}`（:57-66）、`Choice`（:78-86）、`Set`（:88-95，含 `HostedHistoryItem` 服务端工具调用历史 :101-118）。执行流程：转换前 `toolconv.ExtractRequest`（decode.go:16）把 tools 从源格式剥离成 `Set`，messages 逐跳转换，最后 `toolconv.AttachRequest`（encode.go:16）按目标格式编码回去并产出 `ConversionDiagnostic`（如有损降级）。响应侧对应 `ExtractHostedResponse`/`AttachHostedResponse`（response_registry.go:485-504）与流侧 `InspectStreamResponse`（response_registry.go:343）。
3. **reasoning/thinking 有独立抽象**：`relaykit/relayconvert/reasoning/` 包的 `Intent`/`Effort` 模型，`FromOpenAIChat`/`FromGemini`/`ApplyToOpenAIChat`/`sharedclaude.ApplyReasoning` 等成对的提取/应用函数；stop reason 映射集中在 `relaykit/reasonmap/`。

这种设计的含义：写新上游时，messages 只需实现"你的格式 ↔ OpenAI chat"两个方向即可接入全部格式对；工具和 thinking 自动跟随。

## 6. 错误处理与边缘情况

### 6.1 错误模型与格式转换

- 统一内部错误 `types.NewAPIError`（`relaykit/types/error.go:90-99`）：持有 `Err`、`RelayError any`（原始上游错误对象）、`errorType`（openai_error/claude_error/...）、`errorCode`、`StatusCode`、`skipRetry` 标记。
- 上游非 200：`service.RelayErrorHandler`（`service/error.go:87-138`）先用 `dto.GeneralErrorResponse` 兜底解析——该结构同时覆盖 `error`(object/string)、`message`、`msg`、`err`、`error_msg`、`header.message`、`response.error.message` 等各家错误外形（dto/error.go:23-39）；`TryToOpenAIError`（:41）成功则保留上游结构化错误，否则 `ToMessage`（:52）逐级提取纯文本。
- **出口格式按客户端协议转换**：`controller/relay.go:94-112` 的 defer——`RelayFormatClaude` 时输出 `{"type":"error","error":{...}}` 的 Anthropic 形态（`ToClaudeError`，error.go:213-240），其余输出 `{"error":{...}}` 的 OpenAI 形态（`ToOpenAIError`，error.go:180-211）。两个方法都做 `MaskSensitiveInfo` 脱敏（API key 等），且 Claude→OpenAI 时 type 取自 Claude 错误类型，OpenAI→Claude 时 type 取自 OpenAI code。
- 状态码改写：渠道可配 `status_code_mapping` JSON，`service.ResetStatusCode`（service/error.go:140-163）在各 Helper 返回前统一改写（compatible_handler.go:165-166 等）。
- 流内错误：Claude 上游流中的 error 事件经 `claudeResponse.GetClaudeError()` 检出并转成 `types.WithClaudeError`（relay-claude.go:94-96、316-318）；Responses 流有 `ResponseStreamState.FailResponsesStream`（response_registry.go:438-449）发送协议原生的终止错误事件。
- 请求转换失败：`relay/convert_request_error.go:13-23`，`ConversionLossError`（带 diagnostics 的有损转换）和 reasoning 客户端错误映射为 400 + skipRetry。

### 6.2 模型名映射

- 渠道级 `model_mapping` JSON：`relay/helper/model_mapped.go:14-69`，**支持链式重定向**（A→B→C 用链尾）并带环检测（:40-52）；映射失败先回退到去 thinking 后缀的 base model 名再查表（:36-38）；结果写入 `info.UpstreamModelName` 并 `request.SetModelName`（:61-67）。`OriginModelName`（原始请求模型）与 `UpstreamModelName`（实际上游模型）在 RelayInfo 中全程分离（relay_info.go:74/101）。
- 特殊上游的二级映射：AWS `getAwsModelID`（aws/adaptor.go:97，`awsModelIDMap`）、Vertex `claudeModelMap`、Gemini embedding 强制 `models/` 前缀（gemini_handler.go:205）。
- 重试时 `getChannel`（controller/relay.go:334）换渠道后重新走一遍映射。

### 6.3 流截断与异常收尾

- 流状态机都有 finalize 兜底：OpenAI→Claude 的 `FinalizeStreamResponseOpenAI2Claude`（to_claude_messages_resp.go:420-447）在上游没发完就断流时强制关闭所有打开的 content block、补 `message_delta`+`message_stop`；registry 层 `FinalizeStreamResponse`（response_registry.go:360-403）对多跳链逐级 finalize 并把冲刷出的事件继续流过剩余 step。
- finish_reason 与 usage 分离到达的处理：先记 finish_reason 不发终止帧，等 usage-only chunk 到了再合并发 `message_delta`（to_claude_messages_resp.go:215-236、393-400）。
- OpenAI 流侧保留倒数第二帧（`secondLastStreamData`，relay-openai.go:120）应对"部分兼容网关把完整 usage 放倒数第二个事件"。
- 扫描器层：`StreamScannerHandler` 区分 `[DONE]`、EOF、超时（`StreamingTimeout`）、客户端断开（stream_scanner.go:240-302），全部记入 `info.StreamStatus.EndReason`；客户端断开时立即关上游 body 停止消费 token（:298-301）。
- usage 缺失兜底估算见 §4.3；Claude 渠道还会把估算的 BillingUsage 标记 `Estimated:true`（to_oai_chat_resp.go:445-459）。
- 其他边缘：相邻同 role 合并、空 content 填 `"..."`、首条强制 user 占位消息（§3.1）；`content_filter`/`refusal`/`gemini_block_reason` 等安全拦截会写入 `ContextKeyAdminRejectReason` 供管理端审计（relay-claude.go:27-34、relay-openai.go:275-280、relay-gemini.go:39-41）。

## 7. 对你写自己的 relay gateway 的可借鉴要点

1. **注册表 + RelayFormat 路由**比"每个 adaptor 内嵌转换"更可扩展：转换器声明 From/To/Quality，多跳链自动拼接，运行时校验衔接合法性（request_registry.go:114-135）。
2. **OpenAI Chat 当枢纽格式**，新格式只接两根线；但注意其代价——Claude↔Gemini 被标注为 `discouraged`（经两跳有损）。
3. **工具/思考等正交关注点抽 IR**（toolconv、reasoning 包），避免每条转换边重复实现。
4. **流式转换必须是显式状态机**：block index 重映射、tool_call 首帧缓存 PendingArguments、stop 未开 block、usage 与 finish_reason 的时序解耦，这四件事是 SSE 互转的核心难点，new-api 的处理（§4.2）可直接作为参考实现。
5. **错误三段式**：上游错误万能解析（GeneralErrorResponse）→ 内部统一错误（NewAPIError）→ 出口按客户端协议渲染（ToOpenAIError/ToClaudeError）。
6. 工程细节：`common.DeepCopy` 隔离重试、转换后统一做字段删除/参数覆盖（RemoveDisabledFields/ParamOverride）、usage 用 `MergeUsageNonZero` 语义合并、流框架统一带 ping/超时/客户端断开处理。

如需进一步展开某个具体文件（如 `oai_responses/to_oai_chat_stream_resp.go` 的 934 行 Responses↔Chat 流状态机、或 `toolconv/encode.go` 的 1343 行工具重编码细节），可以继续指定。
