### 1.2 完整请求链路（以 Anthropic 分组 `/v1/messages` 为例）

```
客户端 POST /v1/messages
  └─ routes 注册: backend/internal/server/routes/gateway.go:197
  └─ GatewayHandler.Messages: backend/internal/handler/gateway_handler.go:122
      1. 读取原始 body（[]byte）
      2. ParseGatewayRequest(:163)：解析出 model/stream/是否 Claude Code 形状
      3. Claude Code 客户端检测 SetClaudeCodeClientContext(:200)
      4. 并发槽位获取(:243)、计费资格检查(:256)
      5. sessionHash 计算 + 粘性会话选号(:275-318)
      6. 账号 failover 循环(:330+)
      7. 按账号平台分流：
           anthropic → GatewayService.Forward (gateway_forward.go:91)
           gemini    → GeminiMessagesCompatService.Forward (gemini_messages_compat_service.go:583)
           antigravity → AntigravityGatewayService.ForwardGemini / 兼容路径
      8. 返回 *ForwardResult（含 Usage）
      9. 异步 RecordUsage(:578)
```

OpenAI 分组的入口链路类似，handler 在 `backend/internal/handler/openai_gateway_handler.go`（`Messages`:1129、`Responses`:378、`ResponsesWebSocket`:2253），其内部同样是"选号 failover 循环 → 调用 OpenAIGatewayService 的对应 Forward 方法"。

每条 Forward 路径内部骨架高度一致（以 `gateway_forward_as_responses.go:31` 为典型）：

1. 入口 body 归一化（如 `normalizeOpenAIResponsesLegacyIngress` :40）
2. 解析入口 DTO（`json.Unmarshal` → `apicompat.ResponsesRequest` :55）
3. **协议转换**（`apicompat.ResponsesToAnthropicRequest` :63）
4. 强制上游 `stream=true`（:69；上游永远流式，客户端要 JSON 就在网关侧缓冲聚合）
5. **模型映射**（:73-87，见 §7.3）
6. Claude Code OAuth 伪装（:106-116，见 §4.5）
7. cache_control 块数限制（:119）
8. 取凭证（OAuth token / API key）+ 代理
9. `buildUpstreamRequest` 构造上游 HTTP 请求（含 UA、beta 头、身份头）
10. 发送（`DoWithTLS`，带 TLS 指纹伪装）
11. 错误处理与 failover（:154-188）
12. 响应转换：客户端 stream → 逐事件流式转换；客户端非流式 → 缓冲上游 SSE 组装成完整 JSON（:193-197）

**关键设计：上游永远流式。** 所有转换路径都把上游请求强制为 `stream=true`（`gateway_forward_as_chat_completions.go:59`、`openai_gateway_messages.go:135-136`、`gateway_forward_as_responses.go:69`）。客户端要非流式时，网关读完整个上游 SSE 流、拼装成完整响应体再一次性返回 JSON（`handleResponsesBufferedStreamingResponse` :337、`handleAnthropicBufferedStreamingResponse` `openai_gateway_messages.go:566`、`handleChatBufferedStreamingResponse` `openai_gateway_chat_completions.go:495`）。这样只有一套"流式读取"代码，且非流式响应头被显式改回 `application/json`（`gateway_forward_as_responses.go:457`，注释说明了被 SSE Content-Type 污染的坑）。

## 4. 请求转换细节

核心思路（`chatcompletions_anthropic_bridge.go` 文件头注释）：**以 OpenAI Responses API 为枢纽（hub）**，Anthropic ↔ CC 之间另有一座直转桥（避免双状态机串联损耗）。Gemini 不在 hub 内，Anthropic → Gemini 是独立的手写 map 转换。

### 4.1 Anthropic → OpenAI Responses（`anthropic_to_responses.go`，`AnthropicToResponses` :13）

- **system**：Anthropic `system`（string 或 block 数组）→ Responses `input` 中一条 `role=developer` 的 message item（:124-137）。其中 Claude Code 的计费归因块（`x-anthropic-billing-header` 前缀）被识别并过滤（:152-175）
- **messages → input items**：
  - user/assistant 普通 text → message item
  - `tool_result` 块 → `function_call_output` item；其中嵌的图片被提取成单独的 user message（图片在 Responses 里不能挂在 function_call_output 上）（:216-244）
  - assistant 的 `thinking` 块（带 `signature`）→ `reasoning` item 的 `encrypted_content`；签名以 `gAAAA` 开头的（Google 系）跳过不转（:285-299）
  - `tool_use` 块 → `function_call` item
- **tools**：`web_search_*` 系列映射为 `{type:"web_search"}`（:445-462）
- **tool_choice**：`auto`→`auto`，`any`→`required`，`none`→`none`，`{type:"tool",name}`→`{type:"function",name}`（:89-114）
- **参数映射**：`max_tokens`→`max_output_tokens`（下限 128）；`thinking.effort=max`→`reasoning.effort=xhigh`（:435）；gpt-5 系模型剔除 `temperature`/`top_p`（:35, :472）
- **thinking → reasoning**：Anthropic `thinking:{type:"enabled",budget_tokens}` ↔ Responses `reasoning:{effort, summary:"auto"}`，并要求 `include:["reasoning.encrypted_content"]` 以便回程还原签名

### 4.2 OpenAI Responses → Anthropic（`responses_to_anthropic_request.go`，`ResponsesToAnthropicRequest` :13）

- `instructions` + input 中 system/developer 消息拼接为 Anthropic `system`
- `function_call` item → assistant `tool_use` 块；`function_call_output` → user `tool_result` 块（:153）
- **`reasoning` item 直接丢弃**（:167-173）——无法伪造 Anthropic 的加密 signature，只能丢（反向方向的 signature→encrypted_content 是可行的，正向不可行）
- 空内容消息丢弃防上游 400（:182, :197）
- **结构修复**：`normalizeAnthropicToolPairing`（:311）修复 tool_use/tool_result 邻接不变式（Anthropic 要求 tool_result 必须紧跟对应 tool_use 的下一条 user 消息）；`mergeConsecutiveMessages`（:576）合并连续同角色消息保证角色交替
- `max_output_tokens`→`max_tokens`，默认 8192（:32-38）
- effort 反向映射 `xhigh`→`max`（:93）；effort≠low 时自动启用 thinking 并给默认 budget（:55-65，默认 budget 常量 :71）

### 4.3 Chat Completions → Responses（`chatcompletions_to_responses.go`，`ChatCompletionsToResponses` :18）

- role 映射：system→developer message item、user→user、assistant→assistant、tool→`function_call_output`、旧式 `function` role 兼容
- assistant 的 `reasoning_content` 被包成 `<thinking>...</thinking>` 文本放回 content（:168-170）——CC 的明文推理无法变成 Responses 的 reasoning item
- `functions[]` 旧式工具兼容；`reasoning_effort`→`reasoning:{effort, summary:"auto"}`（:66）
- 强制 `stream=true`、`store=false`、`include=[reasoning.encrypted_content]`（:29-47）
- `x_search`/`web_search` 工具透传（:427）

### 4.4 Anthropic ↔ Chat Completions 直转桥（`chatcompletions_anthropic_bridge.go`）

`AnthropicToChatCompletionsRequest`（:42）：
- system → system 消息；`tool_result` → `role=tool` 消息；`tool_use` → `tool_calls`
- **thinking 块 → `reasoning_content`，但仅在该 assistant 消息带 tool_calls 时才保留**（:292, :313）——DeepSeek 等上游要求带工具调用的轮次必须回传 reasoning_content，其余轮次丢弃
- `web_search` 工具丢弃（CC 无对应物）（:329-346）
- tool_choice 校验目标工具已声明（:358）

### 4.5 Claude Code 客户端兼容（mimicry 伪装）

这是本仓库最有特色的部分。两个方向：

**识别真实 Claude Code 客户端**（`backend/internal/service/claude_code_validator.go`）：
- UA 正则 `claude-cli/x.x.x`（:19）
- 官方 system prompt 模板列表（:30-48），用 **Dice 系数**（bigram 相似度，:308）阈值 0.5 匹配（:25）
- 计费归因块识别：`x-anthropic-billing-header` 前缀 + `cc_entrypoint=` 标记（:60-64，:217-220）
- 完整校验链 `Validate`（:84）：UA → 路径豁免（count_tokens、max_tokens=1 探测请求）→ system 相似度 → X-App/anthropic-beta/anthropic-version 头 → `metadata.user_id` 格式
- `isClaudeCodeClient`（`gateway_upstream_response.go:35`）：UA + metadata.user_id

**伪装成 Claude Code**（OAuth 账号 + 非 Claude Code 入口时必须伪装，否则 Anthropic 判为第三方应用扣 extra usage）：
- 触发条件：`shouldMimicClaudeCode = account.IsOAuth() && !isClaudeCode`（`gateway_forward.go:196`；`gateway_forward_as_responses.go:111-116` 注释明确说 Responses 入口"永远不是 Claude Code 客户端，所以必须完整执行伪装链路"）
- `applyClaudeCodeOAuthMimicryToBody`：system prompt 重写（注入官方 CLI system 块）+ `normalizeClaudeOAuthRequestBody`（`gateway_forward.go:233`）+ 工具名混淆（:244）+ metadata.user_id 注入
- 其他归一化：dateline 归一化（:262）、`enforceCacheControlLimit`（:269，cache_control 断点数上限）
- OAuth 账号的模型 ID 归一化：`claude.NormalizeModelID`（`backend/internal/pkg/claude/constants.go:231`），短名→带日期长 ID（`ModelIDOverrides` :217-221）
- Anthropic 原生路径的前置过滤器链（`gateway_forward.go`）：`StripEmptyTextBlocks`(:340)、`FilterWebSearchHistoryBlocks`(:347)、`FilterThinkingBlocks`(:360)、`NormalizeChineseLLMThinking`(:365)
- **thinking 签名 400 两阶段降级重试**（`gateway_forward.go:400-490`）：上游拒绝 thinking 签名时剥离签名重试

### 4.6 Gemini 方向请求转换（手写 map，不在 apicompat hub 内）

`convertClaudeMessagesToGeminiGenerateContent`（`gemini_messages_compat_service.go:3260`）：
- system → `systemInstruction`；messages → `contents`（role user/model）
- `tool_use` → `functionCall` + `thoughtSignature`；`tool_result` → `functionResponse`
- image base64 → `inlineData`
- **`ensureGeminiFunctionCallThoughtSignatures`：对缺失签名的 functionCall 注入 dummy 签名 `"skip_thought_signature_validator"`**（:43-44）——Gemini 3 要求 functionCall 必须带 thoughtSignature
- `cleanToolSchema`（:3610）清理 Gemini 不支持的 JSON Schema 字段
- 三种上游形态构造：AI Studio APIKey(:626) / Code Assist v1internal wrapped request(:679) / Vertex(:734)

Antigravity 方向：`TransformClaudeToGeminiWithOptions`（`pkg/antigravity/request_transformer.go:87`）：web_search 工具降级到 gemini-2.5-flash(:96-100)、`ensureMaxTokensGreaterThanBudget`(:74)、`generateStableSessionID`(:24，优先取 metadata.user_id :178-180)、toolConfig VALIDATED(:154)。

## 5. 响应转换

### 5.1 非流式响应

统一模式：**上游强制流式 → 网关缓冲聚合 → 转目标协议 JSON**。

- Anthropic 上游 → Responses：`handleResponsesBufferedStreamingResponse`（`gateway_forward_as_responses.go:337`）逐事件扫描，`message_start` 取骨架、`content_block_start/delta` 累积 content（text 拼接、thinking 拼接、`input_json_delta` 用 `appendRawJSON` 拼 JSON 片段 :644-655，特判 content_block_start 自带的 `{}` 占位 :646-652）、`message_delta` 取 stop_reason/usage，最后 `AnthropicToResponsesResponse`（:446）转换并强制 Content-Type 回 JSON（:457）
- Responses 上游 → Anthropic：`readOpenAICompatBufferedTerminal`（`openai_gateway_messages.go:577`）读 SSE 直到 terminal 事件（`response.completed/incomplete/failed`，判定列表 :676-683）；若 terminal 事件 `output` 为空，用 `BufferedResponseAccumulator.SupplementResponseOutput`（:641）从累积的 delta 重建完整 output；然后 `ResponsesToAnthropic`（:643）
- Responses 上游 → CC：`handleChatBufferedStreamingResponse`（`openai_gateway_chat_completions.go:495`）→ `ResponsesToChatCompletions`（:574）
- CC 上游 → Anthropic：`bufferChatCompletionsAsAnthropic`（`openai_gateway_messages_chat_fallback.go:140`）→ `ChatCompletionsResponseToAnthropic`（:155）

非流式转换函数本体：`ResponsesToAnthropic`（`responses_to_anthropic.go:17`）——reasoning→thinking 块（signature=encrypted_content :36-45）、message→text、function_call→tool_use、`web_search_call`→`server_tool_use`+`web_search_tool_result` 成对块（:62-81）、stop_reason 推导（:121）。反向 `AnthropicToResponsesResponse`（`anthropic_to_responses_response.go:18`）。

### 5.2 SSE 流式：逐 chunk 状态机映射

每个方向一个**有状态转换器**（State 结构 + 每事件转换函数 + Finalize 兜底函数）。调用侧模式统一：扫上游 SSE 行 → 解析事件 → 转换函数产 0..N 个目标事件 → 逐个写客户端 → Flush（如 `handleResponsesStreamingResponse` `gateway_forward_as_responses.go:483-641`）。

**Responses 流 → Anthropic 流**（`responses_to_anthropic.go`，`ResponsesEventToAnthropicState` :175 / `ResponsesEventToAnthropicEvents` :213 / `FinalizeResponsesAnthropicStream` :254）：

| Responses 事件 | Anthropic 事件 |
|---|---|
| `response.created` | `message_start`（stop_reason=null，:315） |
| `response.output_item.added`(function_call/reasoning/message) | `content_block_start`（tool_use / thinking / text） |
| `response.output_text.delta` | `content_block_delta`(text_delta) |
| `response.function_call_arguments.delta` | `content_block_delta`(input_json_delta)；Read 工具 `pages=""` 清洗（:433） |
| `response.reasoning_summary_text.delta` | `content_block_delta`(thinking_delta)（:520） |
| 关闭 thinking 块前 | 先发 `signature_delta`（携带 encrypted_content）（:688） |
| `response.completed` | `message_delta`（stop_reason+usage）+ `message_stop`（:625） |
| 流异常结束 | Finalize 兜底关块 + message_stop（:254） |

**Anthropic 流 → Responses 流**（`anthropic_to_responses_response.go`，`AnthropicEventToResponsesState` :140 / `AnthropicEventToResponsesEvents` :197）：

| Anthropic 事件 | Responses 事件 |
|---|---|
| `message_start` | `response.created` |
| `content_block_start`(thinking/text/tool_use) | `response.output_item.added`（+`response.content_part.added` :336） |
| `content_block_delta`(text_delta) | `response.output_text.delta` |
| `content_block_delta`(thinking_delta) | `response.reasoning_summary_text.delta` |
| `content_block_delta`(input_json_delta) | `response.function_call_arguments.delta` |
| `content_block_delta`(signature_delta) | **丢弃**（:411-413）——签名已在 output_item.done 的 reasoning item 里 |
| `message_stop` | `response.completed`（携带累积的完整 Outputs :500，供 SDK `get_final_response`） |

**Responses 流 → CC chunk**（`responses_to_chatcompletions.go`，`ResponsesEventToChatState` :118 / `ResponsesEventToChatChunks` :146）：created→role chunk、text.delta→content delta、`output_item.added`(function_call)→tool_calls 首 chunk（带 index/id/name）、args delta 经 OutputIndex→ToolIndex 映射、reasoning delta→`reasoning_content` delta、completed→finish chunk + 独立 usage chunk。

**CC chunk → Anthropic 流**（直转桥，`ChatCompletionsToAnthropicStreamState` :557 / `ChatCompletionsChunkToAnthropicEvents` :614 / `FinalizeChatCompletionsAnthropicStream` :678）：
- `reasoning_content` delta → thinking 块；content → text 块
- **tool_calls 按 index 延迟宣告**：name 未到的 chunk 先缓存参数（:793-848），空参数补 `"{}"`（:921）
- Finalize 发 message_delta + message_stop（:678）

**CC chunk → Responses 流**：`ChatCompletionsChunkToResponsesEvents`（`openai_gateway_responses_chat_fallback.go:224` 调用），结束 `FinalizeChatCompletionsResponsesStream`(:262) + `[DONE]`(:267)。

**双状态机串联**的典型案例：CC 入口 → Anthropic 上游的流式路径 `handleCCStreamingFromAnthropic`（`gateway_forward_as_chat_completions.go:354`）：`AnthropicEventToResponsesEvents` → `ResponsesEventToChatChunks`（:437-445），一个 Anthropic 事件经过两个状态机变成 CC chunk。

**Gemini 流式**是独立的手写转换（不走状态机 DTO）：`handleStreamingResponse`（`gemini_messages_compat_service.go:2104`）map-based SSE → Anthropic 事件序列（message_start/content_block_start/delta/stop/message_delta/message_stop），text 差分用 `computeGeminiTextDelta`，tool_use id 合成 `toolu_`+randomHex。

### 5.3 usage 统计与语义换算

usage 语义差异是三大协议间最容易踩坑的点，代码中全部显式处理：

- **Anthropic**：`input_tokens` **不含** cache read/creation（另有 `cache_creation_input_tokens`/`cache_read_input_tokens` 字段，含 5m/1h 分层）——`ClaudeUsage`（`gateway_service.go:595-603`）
- **Responses**：`input_tokens` **包含** cached_tokens（`input_tokens_details.cached_tokens`）
- 换算：`anthropicUsageFromResponsesUsage`（`responses_to_anthropic.go:98`）input = InputTokens − cached − cacheCreation；反向 `AnthropicToResponsesResponse` 把 cache 加回 input_tokens（`anthropic_to_responses_response.go:104-117`）
- **Gemini**：`promptTokenCount` 含 `cachedContentTokenCount`；`extractGeminiUsage`（`gemini_messages_compat_service.go:2978`）input=prompt−cached，output=candidates+thoughts
- **国产上游兼容**：`mergeAnthropicUsage`（`gateway_forward_as_responses.go:277-321`）优先采用 OpenAI 风格的 `prompt_tokens`/`prompt_cache_hit_tokens`/`prompt_cache_miss_tokens` 权威值，覆盖 Kimi 流式语义变化与 GLM/DeepSeek cache 别名
- CC 直转桥 usage：`chatUsageToAnthropicUsage`（`chatcompletions_anthropic_bridge.go:517`）
- Anthropic 原生透传流式的 usage 补丁：`parseSSEUsage`/`sseUsagePatch`/`extractSSEUsagePatch`（`gateway_upstream_response.go:1158/:1173/:1188`）——流中途从 SSE 提取 usage 并 patch

usage 经 `ForwardResult`/`OpenAIForwardResult`（`gateway_service.go:611` / `openai_gateway_service.go:233`）带回 handler，异步 `RecordUsage` 计费；流式路径还记录 `FirstTokenMs`（首字时间）。

## 6. 数据结构

**全部 DTO 集中在 `backend/internal/pkg/apicompat/types.go`**，按协议分三组：

- **Anthropic**：`AnthropicRequest`(:17，system 为 `json.RawMessage` 兼容 string/数组、messages/tools/thinking/output_config.effort/metadata)、`AnthropicContentBlock`(:56，text/thinking+signature/image/tool_use/tool_result/cache_control)、`AnthropicStreamEvent`(:185)、`AnthropicDelta`(:203，text_delta/input_json_delta/thinking_delta/signature_delta)、`AnthropicUsage`(:165，含 prompt_tokens/cached_tokens 兼容字段)
- **Responses**：`ResponsesRequest`(:228)、`ResponsesInputItem`(:262，自定义 `UnmarshalJSON` 容忍 output 字段非字符串 :284)、`ResponsesTool`(:324，容忍字符串简写 :344)、`ResponsesOutput`(:393，tool_search_call 特殊 Marshal :424)、`ResponsesUsage`(:505，**超宽容 UnmarshalJSON** :516，兼容 prompt_tokens/cache_write 等各种第三方拼写)、`ResponsesStreamEvent`(:607)
- **Chat Completions**：`ChatCompletionsRequest`(:654)、`ChatMessage`(:683，`reasoning_content` 与 `reasoning` 双字段兼容)、`ChatCompletionsChunk`(:803)、`ChatDelta`(:822)

**中间表示策略：混合模式，不是纯统一 IR 也不是纯两两直转**：
- 枢纽：OpenAI Responses API 是事实上的 hub（Anthropic↔CC 之外的转换都经它中转，如 CC→Anthropic 走 `ChatCompletionsToResponses`→`ResponsesToAnthropicRequest` 两跳）
- 例外一：Anthropic↔CC 直转桥（`chatcompletions_anthropic_bridge.go`）跳过 hub，单状态机
- 例外二：Gemini/Antigravity 完全在 hub 外，Anthropic DTO ↔ Gemini map 手写转换

DTO 设计的两个值得学习的点：
1. **宽容反序列化**（`UnmarshalJSON` 覆盖）应对第三方 OpenAI 兼容上游的字段拼写漂移
2. `json.RawMessage` 保留不确定结构（system、metadata、tool input），配合 gjson/sjson 做字段级改写（如 `openai_gateway_chat_completions.go:202` 用 `sjson.SetBytes` 只改 model 字段透传原始 body）

## 7. 特殊处理

### 7.1 账号池 / 负载均衡与协议转换的交互

- **粘性会话**：handler 层从请求体算 sessionHash（`gateway_handler.go:275-318`），同会话优先落同一账号——对协议转换的意义在于：**thinking signature / encrypted_content 是账号绑定的**，换账号后上游无法解密历史中的加密 reasoning
- **failover 循环**：`UpstreamFailoverError`（`gateway_service.go:686-703`）携带丰富元数据（RetryableOnSameAccount、SameAccountRetryMax、SafeToFailoverAfterWrite、Stage/Scope/Reason），转换层在错误时构造它抛回 handler 换号重试
- **Grok 换账号解密失败**的专门处理：`isGrokInvalidEncryptedContentResponse`（`openai_gateway_grok.go:277`）命中时，剥离请求历史中的 thinking 签名（`stripAnthropicThinking
`stripAnthropicThinkingSignatures`（`openai_gateway_grok.go:436`）剥掉历史中的 thinking 签名后整体重试一次（`openai_gateway_messages.go:458-467`）；出站方向还有一次 strip+retry 循环（`openai_gateway_messages.go:383-429`）——出站 body 仍带 `reasoning.encrypted_content` 时，任何 400 都先剥离重试再视为硬失败
- **会话续传与 prompt cache**：OpenAI 方向用 `prompt_cache_key` + `session_id` 头维持上游 prompt cache（`openai_gateway_messages.go:348-354`：session_id 由 `apiKeyID + 账号身份 + promptCacheKey` 隔离派生成 UUID，保证不同 API key 产生不同上游会话）；`previous_response_id` 续传（:114-116, :147-150），失效时自动降级重试（:442-454）
- **同账号重试**：临时性错误（Google 间歇 400、空响应）可在同一账号重试 N 次再切号（`UpstreamFailoverError.RetryableOnSameAccount` 等字段，`gateway_service.go:691-694`）
- **流式中途失败不可换号**：一旦已向客户端写出语义内容，failover 会把两个模型的流拼接在一起，所以流式错误处理里显式判断 `!clientOutputStarted && shouldFailover` 才允许换号，否则转成对应协议的流内 error 事件发给客户端（`openai_gateway_messages.go:1046-1083`）

### 7.2 错误格式转换

每种客户端协议有自己的错误 JSON 外形，网关在各自出口写对应格式：

| 函数 | 位置 | 格式 |
|---|---|---|
| `writeAnthropicError` | `openai_gateway_messages.go:1324` | `{"type":"error","error":{"type":...,"message":...}}` |
| `writeChatCompletionsError` | `openai_gateway_chat_completions.go:1148` | `{"error":{"type":...,"message":...}}` |
| `writeResponsesError` | `gateway_forward_as_responses.go:658` | `{"error":{"code":...,"message":...}}` |
| 流内错误 | `buildAnthropicStreamErrorSSE`（`openai_gateway_messages.go:1338`）/ `buildChatStreamErrorSSE`（`openai_gateway_chat_completions.go:1162`） | SSE error 事件 / error chunk + `[DONE]` |

- **错误透传规则服务**：`backend/internal/service/error_passthrough_service.go`——按关键词/平台/错误码匹配规则决定是否把上游错误原文透传给客户端（8KB body 匹配窗口 :56）；流式场景统一走 `applyOpenAIStreamFailedErrorPassthroughRule` 做语义状态推断 + body 归一化（`openai_gateway_messages.go:1061-1069`、`openai_gateway_chat_completions.go:807-815`），因为 `response.failed` 事件到达在 HTTP 200 的 SSE 流上、没有真实 HTTP 错误码
- **状态码映射**：`mapUpstreamStatusCode`（`gateway_forward_as_responses.go:669`）上游 5xx → 客户端 502，其余透传
- **cyber_policy 特例**：OpenAI 上游风控拦截（流内 `response.failed`）不可重试、不 failover，按当前客户端协议格式写错误 + 记 tokens=0 免费用量行（`openai_gateway_messages.go:597-633`、`openai_gateway_chat_completions.go:521-560`）
- Gemini 方向：`mapGeminiErrorBodyToClaudeError`（`gemini_messages_compat_service.go:2006`）+ `mapGeminiStatusToClaudeErrorType`（:2048）把 Google 错误码映射成 Anthropic error type

### 7.3 模型名映射（三级）

1. **账号级显式映射** `Account.GetMappedModel`（`account.go:865`）→ `ResolveMappedModel`（:872）：支持通配符、最长优先匹配；未命中时对请求模型做归一化再查一次（:880-885）
2. **协议级归一化** `claude.NormalizeModelID`（`backend/internal/pkg/claude/constants.go:231`）：OAuth 短名→带日期长 ID（`ModelIDOverrides` :217-221），回程 `DenormalizeModelID`（:242）还原短名；Vertex 另有 `normalizeVertexAnthropicModelID`
3. **上游级适配**：`normalizeOpenAIModelForUpstream`（OpenAI 方向）；Codex transform 可能二次归一化模型名（`codexResult.NormalizedModel`，`openai_gateway_messages.go:231-233`）

响应回程时把模型名改回客户端请求的原名（如 `responsesResp.Model = originalModel`，`gateway_forward_as_responses.go:447`）；同时 `UpstreamResponseModel` 记录上游真实返回的模型名并检测冲突（`ForwardResult.UpstreamResponseModel/Conflict`，`gateway_service.go:620-623`）。

### 7.4 thinking / reasoning 字段往返（三种签名的互认）

这是跨协议转换中最微妙的字段，三种协议的"推理"形态完全不同：

| 协议 | 形态 |
|---|---|
| Anthropic | `thinking` 块 + 加密 `signature`（必须原样回传才能多轮续推理） |
| OpenAI Responses | `reasoning` item + `encrypted_content` + 明文 `summary` |
| Chat Completions | 明文 `reasoning_content` 字符串（无签名概念） |

往返规则在代码中的落点：

- **Anthropic → Responses**：thinking.signature → reasoning.encrypted_content；`gAAAA` 前缀（Google 系签名）跳过（`anthropic_to_responses.go:285-299`）
- **Responses → Anthropic**：reasoning.encrypted_content → thinking.signature（`responses_to_anthropic.go:36-45`）；流式在关 thinking 块前发 `signature_delta`（`responses_to_anthropic.go:688`）；反向 `signature_delta` 事件直接丢弃（`anthropic_to_responses_response.go:411-413`）
- **Responses → Anthropic 请求方向**：reasoning item **无法伪造 Anthropic 签名，直接丢弃**（`responses_to_anthropic_request.go:167-173`）——单向有损
- **Anthropic → CC**：thinking → `reasoning_content` 明文，但仅在带 tool_calls 的轮次保留（DeepSeek 约束，`chatcompletions_anthropic_bridge.go:292,313`）
- **CC → Responses**：`reasoning_content` 包 `<thinking>` 标签塞进 content 文本（`chatcompletions_to_responses.go:168-170`）——CC 明文推理没有对应的 Responses item 形态
- **effort 等级映射**：Anthropic `output_config.effort=max` ↔ Responses `reasoning.effort=xhigh`（`anthropic_to_responses.go:435` / `responses_to_anthropic_request.go:93`）；effort≠low 时自动启用 thinking + 默认 budget（`responses_to_anthropic_request.go:55-65`）
- **明文 reasoning 缓存自愈**：Responses→CC 桥接时客户端可能只回传 encrypted-only 的 reasoning item（无明文 summary），网关按 reasoning item id 把明文存入缓存（TTL 7 天，`openai_gateway_responses_chat_fallback.go:308`），回程用 `reasoningContentByID`（:314）回注 `reasoning_content`；失败 fail-open（:311-313）；请求历史里带明文的 item 顺手回写缓存自愈 Redis 漂移（`recacheReasoningItemsFromInput` :330）
- **Grok 特判**：换账号后 encrypted_content 解密失败 → 剥离签名重试（见 §7.1）；Grok reasoning effort 归一化（`openai_gateway_grok.go:661,702`）
- **Gemini**：`thoughtSignature` 挂在 functionCall 上，缺失时注入 dummy 签名 `"skip_thought_signature_validator"`（`gemini_messages_compat_service.go:43-44`）

## 8. 总结：可借鉴的设计要点

1. **Hub + 直转桥混合**：以 OpenAI Responses 为枢纽减少转换器数量（O(n) 而非 O(n²)），但对高频/有损路径（Anthropic↔CC）保留直转桥避免双状态机串联的延迟与信息损耗。
2. **上游永远流式**：统一只有一套流式读取代码；非流式 = 缓冲聚合 + 显式修正 Content-Type。
3. **每方向一个 SSE 状态机**（State + Events 函数 + Finalize 兜底），Finalize 保证异常断流也能产出合法的 message_stop/[DONE]。
4. **usage 语义显式换算**：cache token 的"含/不含"差异在每个转换器入口就地处理，另设宽容反序列化应对第三方拼写漂移。
5. **签名类字段（thinking.signature / encrypted_content / thoughtSignature）按"账号绑定"对待**：粘性会话保证同账号、换账号时剥离重试、缺失时注入 dummy。
6. **身份伪装与协议转换正交**：Claude Code mimicry / Codex instructions 模板 / 身份头恢复都封装成独立的 body 变换函数，插在"协议转换完成、发送之前"。
7. **宽容解析 + 字段级改写**：DTO 用 `json.RawMessage` + 自定义 UnmarshalJSON 容忍漂移；只需改少数字段时用 gjson/sjson 直接改原始 body，避免全量重建丢字段。
